# Desktop performance audit, November 2026

Baseline of the desktop app on `origin/dev` at `1b1844b` (16 November 2026),
measured before the optimisation round. Every number below can be measured
again with the tools added with this report (see [Reproduce](#reproduce)).
The fix packages and their issues are listed at the end.

## Test machine

All runs that start the app were made on the test VM (Proxmox VM 111), not
on a developer desktop. Only the headless Go benchmarks ran on a
workstation.

| | |
| --- | --- |
| CPU | 3 vCPUs, host CPU Intel Core i5-10210U @ 1.60 GHz (`cpu: host`) |
| RAM | 4 GB configured, 2.2 GB visible to the guest (balloon) |
| OS | Ubuntu 26.04.1 LTS, KDE Plasma on Wayland (kwin_wayland); 1loop's default X11 build, through Xwayland |
| Screen | Virtual-1 at 1280 × 800, 75 Hz. 1loop's window is 1180 × 760, scale 1 |
| GPU, run 1 | `vga: virtio`, no 3D: Mesa 26.0.8 **llvmpipe** (the CPU draws everything) |
| GPU, run 2 | `vga: virtio-gl` (set for the run, then set back): **virgl** on the host's Intel UHD (CML GT2), OpenGL 4.3, Mesa 26.0.8 |
| Go | go1.25, the binary built with `go build ./cmd/1loop`, not stripped |

Unless a table says otherwise, the numbers are from the **virgl** run, the
setup closest to a real laptop. The llvmpipe run is the floor: what a
machine without a working GPU driver gets (software_gl, #412).

The synthetic state (`scripts/perf/genstate`) has 200 chats in 30 projects
(a third of them subchats) and one long chat of **4,000 rows**: prompts,
answers with lists and code blocks, `shell`/`read_file`/`edit_file`/
`search_files` tool rows with output, and a 640 × 400 picture every 150
rows. `state.json` is 8.1 MB.

What runs on the main thread before the first frame, in order:
`claimInstance`, `watchCrashes`, `fyneapp.NewWithID` (3 ms),
`CreateSplashWindow` (GLFW + GL context, ~20 ms), `openUsage`, waiting
for the state, `loadFrom` (5 ms), `ui.build` (**~150 ms even with an empty
state**, 135–310 ms with this one), `syncBackdrop`, `renderChats` (45 ms for
200 chats), `refreshModels`, `startRemote`, `linkServers`, `watchUpdates`,
then `showFirstWindow` (**270–450 ms**: the window mapped and the first GL
frame, which also builds every renderer). Between the first frame and
"interactive" the UI thread is busy for another 250–370 ms (the developer
log reports a 197–204 ms stall each time): the launch animation's first
layouts, `restoreLayout` and `restoreWindows`. Theme fonts, the theme
files and git/worktree scans are not on that path: they start later.

loaded row costs, and does not come back after GC. That is a leak, not a
cache (see A4). Goroutines stay flat (32–35): no goroutine leak.

## Flame-graph findings

1. **Sidebar rows parse their SVG icons again at every render.**
   `tapRow.CreateRenderer` → `tapRowRenderer.Refresh` →
   `svg.NewDecoder` → `oksvg.ReadIconStream` → `encoding/xml`: 54 % of
   `renderChats`' allocations (1.9 GB over the benchmark) and 20 % of its
   CPU. Every themed icon (`theme.NewThemedResource`, colored) is decoded
   from XML again for each row, each time the sidebar is rebuilt (each
   chat switch, rename, run state change, theme change). The same path is
   7 % of a first chat open (copy chips, tool rows).
2. **Opening a chat is quadratic in its rows.** `syncCopies` →
   `transcriptLayout.changed` → `offsetIn` walks the transcript from the
   end for every copy button it toggles: 15 % of a 4,000-row open
   (1.6 s of 10.9 s sampled). `advanceChatLoad` also `reflect.DeepEqual`s
   every item against its snapshot.
3. **Every streamed delta lays out the whole chat.** `turn.render` →
   `relayoutColumn` → `transcriptLayout.MinSize` + `Layout`: both loop over
   every row (map lookups keyed by interface, `runtime.mapaccess2` +
   `interequal` = 37 % of a scroll step). That is why a delta costs 0.75 ms
   in a 50-row chat and 1.68 ms in a 4,000-row one. On the VM it is 19 %
   of the stream's CPU. `ParseMarkdown` re-parses the **whole** answer
   every 60 ms (1.6 MB allocated per delta by the end of a long answer).
4. **Scrolling measures every visible row twice a step.**
   `columnLayout.MinSize` → `transcriptLayout.MinSize` calls `MinSize()` on
   every visible row (and every row never measured) at each step: 42 % of
   the scroll's Go CPU on the VM.
5. **The whole window is repainted at each frame.** In every mode,
   `painter.Paint` → `drawObject` → one `glDrawArrays` per rectangle, line,
   image and text (`drawRectangle`/`drawOblong` 10–20 %, `cgocall` 25–45 %).
   No dirty regions and no batching: a blinking caret repaints the
   sidebar, the transcript and the shader.
6. **The caret redraws the window 8 times a second.** With the composer
   focused (the usual state) the window draws 8 frames/s forever, even
   with Animations off; with nothing focused it draws 0.5/s (the frame
   hook's two-second safety redraw). That is 7.7 % of a core on virgl and
   21 % on llvmpipe for a window where nothing changes. The frame hook
   itself is a never-ending `fyne.Animation`, so Fyne ticks its animation
   loop at the screen rate (≈ 58 turns/s in the developer log) even when
   idle, and `keepKnown` walks the whole tree by reflection every 5 s
   (5.6–9.5 ms each time, "slow" in the log).
7. **A shader background repaints the entire UI at its rate.** At 30 fps
   (the default) every shader frame redraws the whole object tree on top:
   +30 % of a core on virgl and +100 % on llvmpipe versus the plain theme.
   It keeps running at 30 fps while the window is not focused
   (`idleblur` with a shader: 30 fps, 23 % CPU). The docs say it pauses in
   the background, but on X11/Xwayland "not focused" does not pause it.
8. **A palette change rebuilds everything at once.** `setAccent` /
   switching theme: `repaint` walks every object, sets the Fyne theme again
   (all fonts dropped and every text shaped again), `renderChats` rebuilds
   the sidebar: 210 ms, 49 MB per change.
9. **Memory held per row.** `flowText` keeps its shaped atoms and its laid
   out lines for every paragraph of every row, visible or not (101 MB after
   the soak). Streamed answers parsed again keep the previous parses
   alive (finding 3 + the soak's growth).
10. **Allocations per idle frame.** 5,700 allocations and 350 KB per frame
    when nothing changes (12,000 / 730 KB for the rare frame when nothing
    is focused): the painter and the layout walks allocate on each redraw,
    which feeds the GC during scrolls and streams.

## Known issues seen during the audit

- **Flaky `concurrent map writes` in `internal/ui` tests** (`worktrees.go`
  and others): the app's own code changes those maps on the UI thread
  (`fyne.Do`), but under the **test driver `fyne.Do` runs its function on
  another goroutine**. The stream benchmark hit the same crash
  (`transcriptLayout.Layout` from a `time.AfterFunc` → `fyne.Do`) until it
  stopped scheduling timers. A test-only `fyne.Do` that runs inline, or
  draining the queue on the test goroutine, should fix the flakiness for
  every test. Owned by package D (tests only, no product file).
- **#440 transcript overlap** (rows overlapping, big gaps): the cached
  heights in `transcriptLayout.sizes`/`widths` and `chat_view_cache.go`
  are what hotspot 7 replaces; a row measured hidden
  (`measureTranscriptText(..., true)`) at one width and shown at another
  is the most likely cause. Package A must keep #440 in mind and add a
  test for it.

## Reproduce

Headless (any machine):

```sh
go test ./internal/ui -run '^$' -bench Perf -benchmem -count 3
go test ./internal/ui -run '^$' -bench PerfStreamDelta/4000 -cpuprofile cpu.out -memprofile mem.out
```

In the real window (on a test VM, never on a desktop in use):

```sh
go build -o /tmp/1loop ./cmd/1loop
go run ./scripts/perf/genstate -out /tmp/1loop-perf-plain          # 200 chats, a 4,000-row chat
go run ./scripts/perf/genstate -out /tmp/1loop-perf -theme aurora  # the same with the shader theme
PROFILE=1 scripts/perf/run.sh /tmp/1loop /tmp/1loop-perf-plain out/plain \
	idle idleblur scroll stream type sidebar split files theme startup
SECONDS_soak=600 scripts/perf/run.sh /tmp/1loop /tmp/1loop-perf-plain out/soak soak
```

Each mode prints frames, frame-time percentiles, CPU, allocations per
frame, memory after launch / before / after, and the launch milestones;
`PROFILE=1` adds `cpu.pprof`, `heap.pprof`, `allocs.pprof` and
`goroutine.txt`; `out/<mode>.gctrace` has `GODEBUG=gctrace=1`. On a
Wayland session started elsewhere, export `DISPLAY`, `WAYLAND_DISPLAY`,
`XDG_RUNTIME_DIR` and `XAUTHORITY` first. The modes are documented at the
top of `internal/ui/bench.go`.
